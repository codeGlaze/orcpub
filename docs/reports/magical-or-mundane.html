The problem

Nothing could say “this isn’t magic”

Custom items have always been stored in a single list, ::mi/custom-items, and rendered through expand-magic-items. There was no attribute for “is this actually magical?”, so the character builder offered every homemade item under Magic Weapons, Magic Armor and Other Magic Items, and the sheet listed them all the same way.

The fix is one new attribute — but the interesting half is everything that had to not break: roughly a decade of stored items, and every character that ever picked one.

The answer

Three values, not two

::mi/magical? is a new, additive Datomic attribute. Items saved before it existed simply don’t carry it — nothing about them is rewritten to introduce it. mi/classify is the single source of truth and returns three answers, because refusing to guess is what makes this safe to run against real content.

State When Treated as
:magical The owner said so, or the item carries magical mechanics — attunement, modifiers, a non-zero bonus, a type with no mundane form (:wand, :potion…), or a rarity only a magic item can hold. A magic item.
:mundane The owner said so, or it is ordinary gear with no magical signal anywhere and a type real gear comes in. Ordinary gear.
:unreviewed A legacy item with nothing to go on either way — the item builder’s untouched defaults. A magic item, exactly as before. Its owner is asked.

:common rarity and :wondrous-item are deliberately not evidence: both are the item builder’s default values, so they tell us the user accepted a default, not that they made a judgement. Built-in SRD items are magical by definition and never inferred otherwise — a rule, not a coincidence for the next SRD addition to break.

The guarantee

Nobody loses gear

This was the real hazard, and it isn’t about items — it’s about characters. A character stores a bare option key: 

::entity/options {:magic-weapons [{::entity/key :bastard-sword ::entity/value {…}}]}

Move that item out of the Magic Weapons selection and the saved reference no longer matches an option. Its modifiers stop applying and it disappears off the sheet. Silent, and for gear picked years ago.

So nothing moves. Every custom item stays resolvable exactly where it has always lived, marked legacy-only? so the picker simply stops offering it — and mundane items are added to the ordinary Weapons / Armor / Equipment lists. On the sheet, the listing follows the item’s own classification rather than the bucket the character stored it in.

A decade of existing characters get the fix with zero writes to character data. The alternative — migrating every character to move the key — is a write against the whole database to fix a listing problem, where any failure loses gear. Adding an option cannot fail.

In the builder

A question that answers its own label

Magic Item? is a dropdown sitting in the same row as Type and Rarity, using the same control as the fields either side of it. A Not set option appears only while an item is still unclassified and disappears the moment someone chooses — a new item never lands there asking a question it already answered.

Choosing No — mundane hides the magic-only fields: rarity, attunement, the magical bonuses, and the ability / save / speed / resistance / immunity grids. Base weapon and base armor stay for both kinds — damage dice and AC are what an ordinary sword is made of.

Suspended, not deleted

A checkbox must not destroy data

Marking an item mundane suspends its magic rather than deleting it. The stored item keeps everything; a read-time view (effective-item) strips the mechanics on the way out to anything that builds modifiers or displays an item. Switch back and it all returns.

Saved to Datomic

{:db/id 104
 ::mi/name "Rimefang"
 ::mi/type :weapon
 ::mi/rarity :rare
 ::mi/attunement #{:any}
 ::mi/magical-attack-bonus 1
 ::mi/modifiers [{…:cold}]
 ::mi/magical? false}

What the app sees

{:db/id 104
 ::mi/name "Rimefang"
 ::mi/type :weapon
 ::mi/rarity :rare
 ;; attunement — suspended
 ;; attack bonus — suspended
 ;; modifiers — suspended
 ::mi/magical? false}

There is exactly one write path for an item — the builder’s save. No export, autosave or sync touches it, and the builder’s edit path deliberately reads the raw stored item, so one untick can never become permanent on the next save. Ten open-and-save cycles leave the item unchanged; the answer to “how long are they kept?” is indefinitely, until someone clicks remove for good.

Magical properties kept but not applied: attunement, modifiers, an attack bonus.

No character using this item gets them. Set Magic Item? back to Yes to restore.

Nothing automatic can reach this state: an item that classification calls mundane on its own has no magical properties by definition. Only a person ticking the box can create it — and they’re told, in three places.

Self-healing

How a decade of items sorts itself out

Three independent paths, none of which requires anyone to do a chore.

On deploy

Bulk backfill

Runs after schema init on every boot. Additive assertions only, never a retraction; selects only items with no value yet, so re-running is a no-op. Swallows its own failures — it can never block startup.

On save

Editing heals

resolve-classification stamps the value the item was already being treated as, so saving retires a guess without changing the item at all.

Always

Read-time fallback

Anything still unstamped classifies correctly on read, so the fix is live before the backfill ever runs and correct if it never does.

The backfill does not guess. Items it can’t place from evidence are left alone entirely — they keep behaving as magic items and the builder asks their owner instead. And unlike its neighbouring attributes, ::mi/magical? is :db/noHistory too — item history is storage nobody asked for, so the backfill's safety comes from refusing to guess rather than from being able to undo one.

Verified

What’s pinned, not just claimed

281 JVM tests / 1,503 assertions and 218 ClojureScript tests / 632 assertions, all passing; lein fig:build and lein garden once clean. This branch adds 48 tests and 193 assertions. CI only compiles the CLJS, so the browser suite was run against a temporary Node target to actually execute it.

  • Every magical property survives the save path. The serializer whitelists keys — one added without being whitelisted would silently start vanishing. Now a test failure, not a slow leak.
  • A reclassified item stays resolvable in the selection characters already stored it in, while dropping out of the picker.
  • The edit path reads the raw item. If it ever read the stripped view, one untick would become permanent.
  • The backfill is idempotent and never re-asserts an owner’s existing answer. Caught two real bugs during the work: this one, and classification resolving after serialization, which drops ::mi/owner and would have stamped every mundane item magical.
  • A new item is never “Not set”. Hoisted to db/default-item so this is enforced, not a comment.
Deliberately left

Two things I didn’t touch

The Type dropdown writes ::mi5e/armor, not :armor. A namespaced typo means (= :armor type) never matches, so custom armor never gets base-armor selection or AC. Real, adjacent, and it needs its own migration story: stored items carry that value, and changing a stored ::type moves the item between equipment selections — the exact orphaning this branch exists to avoid. Classification recognises the legacy value; the dropdown is untouched. Worth doing next, separately.

Two merge conflicts with feature/content-library-management, both trivial. I copied its health-card CSS byte-for-byte at the same anchor, and verified by trial merge that git dedupes it — one copy, no conflict in that block. The conflicts are its mc-toolbar block landing adjacent (take its side), and save-item, where both branches edited the same let. Those compose: normalise the blank type first, then (mi/from-internal-item (mi/resolve-classification item)) — order matters, since classification reads ::mi/type and ::mi/owner.
